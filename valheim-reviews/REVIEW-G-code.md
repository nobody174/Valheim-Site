# REVIEW-G: Code reviewer (valheim-site)

Reviewer role G (code only, no browser). Repo read at `/home/claude/nobody174/valheim-site` (not modified). Runtime evidence came from a copy under the session scratchpad (`npm ci`, `tsc --noEmit`, `eslint .`, `vitest run`, plus throw-away probe tests that were deleted).

## Verdict (3 lines)
1. The code is tidy, strict-typed and well tested (tsc clean, eslint clean, 58 files / 384 tests pass, 13.8k prod LOC vs 4.4k test LOC). The data layer (one graph, id-based) is the strongest part.
2. The risks are not style. They are: one strict-schema line that can silently hide the owner's whole profile after an app update, a search bug that marks every result row as selected, and "advice" code that guesses (hoard label as USED FOR, "You hold n of m" counting kinds not quantities).
3. Several tests lock the bugs in (a test that asserts "Acorn -> Safe to discard", an `aria-selected` test that cannot fail, circular parser tests). Fix those with the code, or the bugs come back.

## Assumptions
- "Pattern 5/8/11" are the numbered items in BRIEF section 4. I re-verified them in code, not on the live site.
- Counts come from `data/*.json` and from running the real functions in vitest (`quickCard`, `createSearch`, `createAppStore`) on the shipped data, not from estimates.
- I did not run `npm run build`, `validate`, `qa` (needs a browser) or look at the live site. Bundle size claims are not mine to make (role F).
- "Unused export" analysis is a regex scan of `export` names against all other src files; type-only names flagged below are low value.

## The 3 riskiest places
1. **`src/state/model.ts` `ProfileSchema.strict()` + `persistence.ts loadState` + `store.ts:39 saveAll`** (G-01): the only code that can make the owner's progress, notes, portals and character disappear from the UI, triggered by an ordinary deploy.
2. **`src/data/quick.ts` `usedForLine` and `src/features/advisor/advisor.ts`** (G-03, G-04): the code that speaks as an authority to a 10 year old. Both print confident wrong lines today, and tests pin one of them.
3. **`src/features/world/WorldPage.tsx` with `save/fch.ts`, `world/worldFile.ts`, `state/worldMap.ts`** (G-13, G-09, G-12d): largest component, binary parsers tied to one game build, storage in three places, tested only against self-made files. A game patch breaks it silently for the tests and loudly for the owner.

## Protect this
- The single derived graph (`data/graph.ts`, `data/lookup.ts`) and id-based references; the validate script and Zod schemas shared between build and runtime.
- Pure, well-tested computation modules: `weaponStats.ts`, `attackModel.ts`, `stationLevels.ts`, `rankings/*`, `advisor.ts` (apart from G-04), `graphModel.ts` (bounded by `MAX_NODES`/`MAX_FANOUT`).
- Defensive binary reading: `Reader.count()` bound and `need()` checks in `fch.ts:150-200`; clear "newer/older version" messages.
- `src/state/*` shape: immutable `with*` helpers, `StorageLike` injection, versioned keys, export/import with schema validation (fix G-01, keep the design).
- The "confirmed text must not change" test pattern for in-game confirmations; the `data.test.ts`/`completeness.test.ts` data guards; `tools/qa` budget in CI.
- Code quality baseline: `any` count 0, 1 `eslint-disable`, tsc and eslint clean.
